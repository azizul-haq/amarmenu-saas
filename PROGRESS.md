## Architectural Decisions Log (ADR)
* **ADR-001 (Versioned Migrations)**: All database changes must reside in `supabase/migrations/<timestamp>_<name>.sql`. No manual un-versioned dashboard edits.
* **ADR-002 (Tenant Security)**: All tenant-scoped tables must have `restaurant_id` and strict RLS policies tied to authenticated identities.
* **ADR-003 (Currency & Format)**: Currency is BDT (`৳`), stored as `NUMERIC(10,2)`. All timestamps stored in `TIMESTAMPTZ` and formatted in `Asia/Dhaka` time.
* **ADR-004 (Phone Numbers)**: Validated against Bangladeshi mobile format (`^(\+8801|01)[3-9]\d{8}$`) and normalized to `+8801XXXXXXXXX`.
* **ADR-005 (Zero `any` Types)**: Strict TypeScript validation. Form inputs validated via Zod schemas.
* **ADR-006 (Supabase Auth & Session Handling)**: Authentication is driven via Supabase GoTrue Auth with JWT tokens. Role resolution is evaluated from `platform_admins` and `restaurant_staff` tables in `AuthContext`. Route protection is enforced via `ProtectedRoute`.
* **ADR-007 (Tenant Row Level Security)**: All database queries must run under Postgres RLS. Public anon clients can only view active menus and submit customer orders. Authenticated restaurant staff are strictly constrained to `restaurant_id = current_restaurant_id()`. Super admins are granted platform-wide oversight via `is_super_admin()`.
* **ADR-008 (Password-Free Owner Onboarding)**: Restaurant owners never receive plaintext or temporary passwords. On approval, the platform issues an invite / set-password link (`/set-password`) via Edge Function / GoTrue Admin API. The owner sets their permanent password upon first access.
* **ADR-009 (Bilingual Menu & Soft Delete Integrity)**: Menu categories and items store both English and Bengali text (`name_bn`, `description_bn`). To protect customer order historical integrity, item deletion uses soft-deletion (`deleted_at = NOW()`). Postgres RLS policies allow staff full management while preventing soft-deleted items from leaking to storefront customer queries. Variants (sizes and add-ons) are modeled as validated JSONB structures with individual pricing.
* **ADR-010 (Cryptographic Table QR Token & Ordering Verification)**: Each dine-in table is assigned a unique, unguessable 32-character hexadecimal cryptographic token (`qr_token`). Scanning `/menu/:slug?table=<token>` validates both restaurant slug and table token atomically via `verify_table_qr_token`. On valid token detection, the table number is automatically locked for checkout to prevent table spoofing. Manipulated, expired, or soft-deleted table tokens are rejected with a clear customer error.
* **ADR-011 (Server-Side Price Authority, Anti-Tampering, Idempotency & Sequences)**: Client-side prices and totals are never trusted for transaction persistence. The `place_order` procedure resolves base prices, size variants, and add-ons directly from database rows, calculating authoritative subtotals, restaurant NBR VAT (`default_vat_rate`), and totals. Any price deviation between client and server triggers an immediate exception (`Price tampering detected`). Network double-submissions are deduplicated via `idempotency_key`. Gap-free sequential numbers (`ORD-YYYYMMDD-XXXX`) are guaranteed through the atomic `restaurant_order_sequences` table. Spam is blocked via 5-minute rolling rate limits per phone number.
* **ADR-012 (Sanitized Customer Order Tracking & Cart Persistence)**: Anonymous customers track their order status via the dedicated `get_customer_order(order_id)` RPC rather than granting broad anon SELECT on `orders`. Cart state is managed through `CartContext` keyed by `${itemId}_size:${size}_addons:${addons}` and persisted per restaurant slug in `localStorage`. Checkouts are validated using `customerCheckoutSchema` (Zod) enforcing BD phone and table rules. Post-order submission automatically clears the restaurant cart and routes customers to `/order/:orderId` featuring real-time 4-step status progression.
* **ADR-013 (Server-Enforced Order State Machine & Audit History)**: Order status transitions must obey the authoritative state machine enforced at the database level by trigger `trg_validate_order_status_transition`. Illegal jumps (e.g. `pending ➔ completed`) or terminal mutations (e.g. `completed ➔ pending` / `cancelled ➔ ready`) raise PostgreSQL exceptions. Authenticated staff transition orders via `transition_order_status`, which checks caller authorization against `restaurant_id`, records `verified_by`, sets transition timestamps, and appends audit events to `order_status_history`.
* **ADR-014 (Kitchen Display System & Thermal KOT POS Printing)**: Kitchen operations run on dedicated real-time subscriptions filtering active orders (`accepted`, `preparing`, `ready`). Orders verified by waiters emit audio notifications to the kitchen queue. KOT printing utilizes dedicated 80mm thermal receipt styles with bold typography, special instructions isolation, and atomic server print tracking via `record_kot_print(order_id)` to flag duplicate reprints.
* **ADR-015 (Cash Settlement, Fiscal Invoicing & Table Reset Automation)**: Financial settlement is executed atomically via the database procedure `settle_order_bill(order_id, payment_method, tendered_amount, discount, notes)`. It strictly authenticates caller staff permissions, enforces cash tendered >= net payable, generates a gap-free fiscal tax invoice number (`INV-YYYYMMDD-XXXX`), records collection in the tenant-isolated `payments` table, transitions the order to `completed`, and resets the associated dine-in table status to `available`. Normalized `order_items` are maintained via database trigger to preserve transactional line-item integrity independent of unstructured JSON payload changes.
* **ADR-016 (Append-Only Audit Logging & Manager PIN Void Overrides)**: Highly sensitive mutations (voiding active orders, cancelling settled bills, waiving payments) require manager PIN authorization (`crypt` against `restaurant_staff.manager_pin_hash`) and a mandatory non-empty business reason. All void operations are encapsulated within the atomic procedure `void_order_with_pin`, which records an immutable snapshot of old and new states in `audit_logs`. The `audit_logs` table is strictly append-only, enforced at the database level by trigger `trg_prevent_audit_log_mutation` and explicit RLS policies that reject any `UPDATE` or `DELETE` attempt with exception `P0001`.
* **ADR-017 (Daily Cash Drawer Shifts, EOD Z-Reports & Cash Reconciliation)**: Register shifts are tracked in `cash_shifts` with opening floats and closing cash counts. Procedure `close_cash_shift` automatically reconciles physical cash against system-expected cash (`opening_float + cash_sales - cash_refunds`), calculating exact discrepancies (shortages/overages), aggregating multi-tender sales (cash, bKash, Nagad, card), orders count, and manager voids. Shift close generates a standardized 80mm printable fiscal Z-report (`Z-YYYYMMDD-XXXX`) and exportable CSV for daily accounting.
* **ADR-018 (Sales Analytics & Bangladesh NBR Mushak-6.3 VAT Architecture)**: Analytical queries run via server-side stored procedures (`get_restaurant_sales_analytics` and `get_mushak_6_3_report`) ensuring tenant isolation via `current_restaurant_id()` and `is_super_admin()`. Calculations strictly partition Gross Sales (`SUM(total)`), Net Revenue (`SUM(subtotal - discount)`), and NBR VAT (`SUM(tax)`). Bangladesh National Board of Revenue (NBR) Rule 40(1) Mushak-6.3 Tax Invoice Register is generated sequentially linking fiscal invoice numbers (`INV-YYYYMMDD-XXXX`), customer details, net taxable value, applicable VAT rate, VAT collected, and total payable, with 1-click UTF-8 BOM CSV exports for compliant tax filing.
* **ADR-019 (SaaS Subscriptions, Mobile Banking Verification & Grace Period Auto-Lock)**: Platform subscription billing supports Bangladesh's predominant mobile banking workflows (bKash & Nagad) alongside bank transfer. Tenant self-service payment submissions generate pending `subscription_invoices` with unique TrxIDs. Super Admins verify submissions against merchant statements, automatically activating subscriptions, extending validity periods (30 days for monthly, 365 days for annual with 20% discount), and unlocking restaurants. An automated evaluation procedure (`evaluate_subscription_grace_and_lock`) provides a 7-day grace period upon expiry before soft-suspending management dashboards (`blocked`), while preserving dine-in customer QR menus to prevent service interruption.
* **ADR-020 (Super Admin Platform Analytics & Cross-Tenant Oversight)**: Platform-wide analytics run under strict Super Admin authorization (`is_super_admin()`), rejecting unauthorized staff or anon callers with exception `P0002`. Aggregations distinguish between food commerce GMV (`SUM(orders.total)`) and software subscription revenue (`SUM(subscription_invoices.amount)`). Time-series trends format dates in `Asia/Dhaka` timezone (`Mon DD`), while restaurant performance rankings cross-reference orders and subscriptions to surface real-time tenant health without exposing sensitive cross-tenant data to unauthorized actors.
* **ADR-021 (Online Payment Architecture, Merchant Disintermediation & Security Lockdown)**:
  - **No Platform Escrow for Food Payments**: Customer food payments must **never** flow through an AmarMenu-owned merchant account. AmarMenu is a pure B2B SaaS platform, not a payment aggregator or escrow service. Subscription payments (restaurant -> AmarMenu) use AmarMenu's own merchant account, while customer food payments flow directly to each restaurant's individual merchant account. Per-restaurant merchant credentials (encrypted and server-side only) will be configured in a future chunk according to official bKash/SSLCOMMERZ documentation.
  - **Server-Authoritative Amounts**: `initiate_online_payment` derives the payable amount strictly from `orders.total` in the database, rejecting any client-supplied amount.
  - **Execution Privilege Lockdown**: Execution of settlement and terminal functions (`complete_online_payment`, `fail_online_payment`, `execute_online_payment_success`, `cancel_online_payment`) is strictly REVOKED from `PUBLIC`, `anon`, and `authenticated` roles. Only `service_role` can execute settlement routines (verified via `has_function_privilege`).
  - **Simulator Gating**: The frontend simulator UI and PIN/OTP modal are dev/staging only and hidden in production builds (`Pay at counter` displayed). The `simulate-payment` Edge Function is doubly protected, requiring `ENABLE_PAYMENT_SIMULATOR === 'true'` AND `APP_ENV !== 'production'`.
  - **Direct Mutation Protection**: Direct SQL `UPDATE orders` mutations setting `payment_status = 'paid'`, `invoice_number`, or completing orders without settlement authorization are strictly prohibited at the database trigger level with exception `P0007`. Settlement must only occur via authorized procedures (`settle_order_bill`, `complete_online_payment`, or `transition_order_status`).
  - **Audit of SECURITY DEFINER Functions**: All `SECURITY DEFINER` functions in the database must explicitly declare `SET search_path = public, extensions` to protect against search_path hijacking vulnerabilities. Audited via `audit_security_definer_functions()`. Patched functions: `create_restaurant_with_owner`, `restaurant_login`, `admin_login`, `process_order_payment`, `auto_link_staff_auth`, `inspect_policies`.
